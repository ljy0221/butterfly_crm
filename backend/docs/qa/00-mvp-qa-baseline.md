## 1. 적용 범위

- **MVP 데모 시나리오** — 발표용 8~10분 시연 흐름이 끊기지 않는 수준
- **6개 도메인 통합 흐름** — 인증·테넌트 / 고객·이벤트 / 세그먼트 / 캠페인 / 발송 / 분석
- **3개 사용자 역할** — OWNER, OPERATOR, ANALYST (DEVELOPER는 SDK 발행 + 분석 조회만)

본 문서가 다루지 않는 것:
- 부하/성능 (S14P31B101-68 부하 테스트 시나리오에서 다룸)
- 보안 침투 테스트 (S14P31B101-43 운영 정책/보안/감사 에픽에서 다룸)
- 채널 게이트웨이 외부 의존 (FCM/APNS) — Stub 어댑터로 대체 시연

## 2. 도메인별 완료 기준 (Definition of Done — MVP)

| 도메인 | 완료 기준 | 검증 방법 |
|---|---|---|
| **인증/테넌트** | 로그인 → JWT 발급 → project_id 권한 검증이 모든 API에 적용됨. 권한 없는 호출은 403. | 통합 시나리오 #1 (로그인) + 임의 API에 다른 프로젝트 토큰으로 접근 → 403 확인 |
| **고객/이벤트** | SDK → POST /events/actions 적재 OK. notification_logs 부모 검증, attribution 윈도우 30일 안에서 매칭. | 통합 시나리오 #2 + KPI 정의서 §4.2 |
| **세그먼트** | 조건 트리 저장 → 미리보기 모수 즉시 반환 → 캠페인 연결 OK | 통합 시나리오 #3 + 모수가 0이 아닌 결과 |
| **캠페인** | 세그먼트 연결 → 단발 또는 예약 발송 → CampaignMessage 확정 | 통합 시나리오 #3 + DB campaign_messages row 확인 |
| **발송** | 발송 워커 → notification_logs 적재 → status=SENT/DELIVERED → Kafka notification-send-result 토픽 발행 | 통합 시나리오 #3 + Kafka 토픽 메시지 확인 (S14P31B101-177 머지본) |
| **분석** | hourly 집계 → daily 롤업 → 운영 대시보드 6개 KPI 표시 (sent_count, delivered_rate, open_rate, click_rate, convert_rate, audit_log) | 통합 시나리오 #4 + KPI 정의서와 표시값 일치 |

### DoD 우선순위
1. **블로커 없음** — 핵심 흐름 1건이라도 끊기면 데모 자체가 안 됨 → 최우선
2. **숫자 일치** — 어디서 보든 같은 KPI 값 (KPI 정의서 §1 단일 정의 원칙)
3. **권한 누수 없음** — 다른 프로젝트 데이터가 노출되지 않음
4. **감사 로그** — 권한 변경, 캠페인 활성화/중지, 발송 실행이 audit_logs에 남음

## 3. 결함 분류 기준

| 등급 | 정의 | 처리 방침 (Code Freeze 전) | 처리 방침 (Code Freeze 후) |
|---|---|---|---|
| **P0 / Blocker** | 데모 흐름 차단. 데이터 손상. 인증 우회. 다른 테넌트 데이터 노출. | 즉시 수정 + 핫픽스 머지 | 발표 전 핫픽스 필수 |
| **P1 / Critical** | 핵심 기능 일부 동작 안 함. 워크어라운드 있어도 사용자 흐름이 부자연스러움. KPI 숫자 불일치. | Freeze 전 수정 | 발표 시 회피 흐름 + 발표 후 수정 |
| **P2 / Major** | 부가 기능 결함. UI 어색함. 비주류 시나리오 결함. | Freeze 전 가능하면 수정 | 발표 후 수정 |
| **P3 / Minor** | 코스메틱. 로그 메시지. 비핵심 검증. | Freeze 후 백로그 | 발표 후 백로그 |

### 분류 가이드
- **"이게 막히면 발표가 안 되나?" → YES면 P0**
- **"발표 흐름은 가능한데 어색하나?" → YES면 P1**
- **권한·테넌트 격리 관련은 무조건 최소 P1**, 의심되면 P0
- **숫자가 다르게 보이는 건 KPI 단일 정의 원칙 위반 → P0** (대시보드/리포트/API 응답이 같은 정의여야 함)

## 4. 검증 환경

| 환경 | 용도 | DB | 외부 채널 | 비고 |
|---|---|---|---|---|
| **로컬 통합** | 개발 중 단위/슬라이스 테스트 | TestContainers MySQL | Stub 어댑터 | `@Tag("integration")` 분리, CI에서 별도 잡 |
| **Dev** | 도메인 간 통합 흐름 일일 점검 | 공유 dev MySQL | Stub 어댑터 | 매일 오전 발견된 결함 → Jira 이슈화 |
| **Stage** | 데모 리허설용 | 별도 stage MySQL | Stub 또는 Sandbox FCM | Code Freeze 후 데이터 시드, 발표용 시나리오 사전 시연 |

**MVP 범위에서는 실제 FCM/APNS 채널 연동을 데모로 시연하지 않는다.** Stub 어댑터가 SENT 상태를 즉시 반환해 흐름은 그대로 보이되, 외부 의존이 발표를 흔들지 않도록 한다.

## 5. 역할 분담 (QA 책임자)

| 도메인 | 1차 책임자 | 통합 시나리오 검증 |
|---|---|---|
| 인증/테넌트 | 김동현 (역할 1) | 시나리오 #1 |

| 세그먼트 | 남정연 (역할 3) | 시나리오 #3 §1~2 |
| 캠페인 | 이서연 (역할 4) | 시나리오 #3 §3~4 |
| 발송 | (역할 5) | 시나리오 #3 §5 + Kafka 토픽 발행 검증 |
| 분석/감사 | 이재영 (역할 6) | 시나리오 #4 + KPI 정합성 |

## 7. 결함 보고 양식

Jira 이슈 생성 시 다음 형식 권장:

```
제목: [QA-Run#N][P{0|1|2|3}] {도메인}: {한 줄 요약}

## 시나리오
- 시나리오 # {1|2|3|4} - § {스텝}

## 재현 절차
1. ...
2. ...

## 기대
- ...

## 실제
- ...

## 환경
- 브랜치: develop @ {commit}
- 환경: dev / local / stage
- 데이터 시드: {기본 / 별도}

## 첨부
- 로그, 스크린샷, request_id
```

라벨: `qa-run-{N}`, `p{0|1|2|3}`, `domain-{auth|event|segment|campaign|delivery|analytics}`
