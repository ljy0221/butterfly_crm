# Butterfly CRM 포팅 매뉴얼

## 1. 문서 목적

본 문서는 GitLab 저장소를 클론한 뒤 Butterfly CRM 서비스를 로컬 또는 배포 환경에서 빌드, 실행, 배포할 수 있도록 정리한 포팅 매뉴얼이다.

소스코드는 별도 업로드하지 않으며, 제출 시에는 GitLab 루트에 `exec` 폴더를 생성한 뒤 본 문서와 DB 덤프 파일을 함께 업로드한다.

## 2. 프로젝트 개요

- 서비스명: Butterfly CRM
- 서비스 유형: 멀티테넌트 CRM 캠페인 SaaS
- 주요 기능: 회원/프로젝트 관리, 고객 이벤트 수집, 세그먼트 빌드, 캠페인 생성/발송, 알림 로그, 분석 대시보드, 크레딧 결제, AI 캠페인/세그먼트 초안 생성
- 저장소 루트 기준 주요 디렉터리
  - `backend`: Spring Boot 멀티모듈 백엔드
  - `frontend`: 관리자/사용자용 React 대시보드
  - `tester-pwa`: 이벤트/푸시 시연용 PWA
  - `android`: FCM 푸시 시연용 Android 앱
  - `deploy`: Kubernetes, Kustomize, ArgoCD 배포 매니페스트
  - `infra`: Prometheus, Grafana, Loki 등 관측성 구성
  - `scripts`: QA/시연 seed 및 부하 테스트 스크립트

## 4. 로컬 실행 절차

### 4.1 저장소 클론

```bash
git clone <GitLab Repository URL>
cd S14P31B101
```

### 4.2 로컬 인프라 실행

로컬 백엔드는 `backend/docker-compose.yml`의 인프라를 사용한다.

```bash
cd backend
docker compose up -d mysql redis kafka clickhouse
```

로컬 기본 접속 정보는 다음과 같다.

| 서비스 | Host/Port | 계정 |
| --- | --- | --- |
| MySQL | `localhost:3307` | `butterfly / butterfly` |
| Redis | `localhost:6379` | 인증 없음 |
| Kafka | `localhost:9092` | 인증 없음 |
| ClickHouse HTTP | `localhost:8123` | `butterfly / butterfly` |
| ClickHouse Native | `localhost:9000` | `butterfly / butterfly` |

### 4.3 백엔드 실행

로컬 프로파일은 시크릿 없이 실행할 수 있도록 기본값이 설정되어 있다.

```bash
cd backend
./gradlew :butterfly-api:bootRun
```

별도 터미널에서 worker를 실행한다.

```bash
cd backend
./gradlew :butterfly-worker:bootRun
```

Windows PowerShell에서는 다음 명령을 사용한다.

```powershell
cd backend
.\gradlew.bat :butterfly-api:bootRun
.\gradlew.bat :butterfly-worker:bootRun
```

로컬 API 기본 주소는 `http://localhost:8080`이다.

### 4.4 프론트엔드 실행

```bash
cd frontend
npm ci
npm run dev
```

접속 주소는 `http://localhost:5175`이다. 개발 서버는 `/api`, `/sdk` 요청을 `http://localhost:8080`으로 프록시한다.

## 6. DB 구성 및 최신 덤프

### 6.1 스키마 관리

DB 스키마는 `butterfly-api`의 Flyway migration이 관리한다.

위치:

```text
backend/butterfly-api/src/main/resources/db/migration
```

최신 마이그레이션 기준 파일은 다음과 같다.

```text
V1__core_baseline.sql
V2__reporting_baseline.sql
V3__audit_triggers.sql
...
V21__add_foreign_keys.sql
```

신규 DB에서는 `butterfly-api`를 1회 이상 부팅하면 Flyway가 자동으로 스키마를 생성한다. `butterfly-worker`는 Flyway를 비활성화하며, 마이그레이션 주체는 `butterfly-api` 하나로 유지한다.

### 6.2 ERD

ERD 원본 문서는 다음 파일을 참조한다.

```text
backend/docs/erd.md
```

### 6.3 DB 덤프 생성

제출용 최신 DB 덤프는 운영 또는 시연 DB에서 다음 명령으로 생성한다.

```bash
mysqldump \
  -h <MYSQL_HOST> \
  -P <MYSQL_PORT> \
  -u <MYSQL_USER> \
  -p \
  --single-transaction \
  --routines \
  --triggers \
  --default-character-set=utf8mb4 \
  butterfly > exec/butterfly_dump_latest.sql
```

로컬 Docker DB 기준 예시는 다음과 같다.

```bash
mysqldump \
  -h 127.0.0.1 \
  -P 3307 \
  -u butterfly \
  -pbutterfly \
  --single-transaction \
  --routines \
  --triggers \
  --default-character-set=utf8mb4 \
  butterfly > exec/butterfly_dump_latest.sql
```

덤프 복원 예시는 다음과 같다.

```bash
mysql \
  -h 127.0.0.1 \
  -P 3307 \
  -u butterfly \
  -pbutterfly \
  butterfly < exec/butterfly_dump_latest.sql
```

### 6.4 시연 데이터 seed

시연용 seed 스크립트 위치:

```text
backend/scripts/demo-seed
```

실행 순서:

```bash
cd backend/scripts/demo-seed
export MYSQL_HOST=localhost
export MYSQL_PORT=3307
export MYSQL_USER=butterfly
export MYSQL_DB=butterfly
export MYSQL_PASSWORD=butterfly

```

주의사항:

- 신규 DB에서는 `channel_credentials` 테이블 생성을 위해 백엔드를 최소 1회 부팅한 뒤 seed를 실행한다.
- `01-project-and-account.sql`의 bcrypt placeholder는 실제 해시로 교체해야 한다.
- FCM 푸시 시연이 필요하면 `firebase-service-account.json`을 `backend/scripts/demo-seed`에 별도로 배치한다. 이 파일은 Git에 커밋하지 않는다.

```bash

export GHCR_USERNAME=<github_or_ghcr_username>

```

API 이미지 빌드:

```bash

./gradlew :butterfly-api:jib
```

Worker 이미지 빌드:

```bash
cd backend

```

기본 base image는 `eclipse-temurin:21-jre`이고, 컨테이너 프로파일은 `prod`가 기본 주입된다.

Secret 예시는 다음 파일을 기준으로 작성한다.

```text
deploy/k8s/overlays/dev/secrets.yaml.example
```

운영 cluster에는 최소 다음 Secret이 필요하다.

| Secret | Key | 설명 |
| --- | --- | --- |
| `mysql-secret` | `root-password`, `app-password` | MySQL root/app 비밀번호 |
| `app-secret` | `jwt-secret` | JWT 서명 키 |
| `regcred` | Docker registry auth | GHCR pull secret |
| `toss-secret` | `client-key`, `secret-key` | Toss Payments 키 |
| `mail-secret` | `username`, `password` | SMTP 계정 |
| `clickhouse-secret` | `username`, `password` | ClickHouse 계정 |
| `openai-secret` | `api-key` | OpenAI API key |

GHCR pull secret 생성 예시:

```bash
kubectl create secret docker-registry regcred \
  --docker-server=ghcr.io \
  --docker-username=<GHCR_USERNAME> \
  --docker-password=<GHCR_TOKEN> \
  --docker-email=<EMAIL> \
  --namespace=butterfly
```

```bash
kubectl apply -k deploy/k8s/overlays/dev
```

배포 확인:

```bash
kubectl get pods -n butterfly

kubectl logs -n butterfly deploy/butterfly-api
```

```bash
curl http://<API_HOST>/actuator/health
```

### 8.4 운영 배포 프로파일

Kubernetes 배포 시 API는 다음 프로파일을 사용한다.

```text
SPRING_PROFILES_ACTIVE=api,prod
```

Worker는 다음 프로파일을 사용한다.

```text
SPRING_PROFILES_ACTIVE=worker,prod
```

`prod` 프로파일에서는 JWT 인증 및 인가가 활성화된다. 로컬 인증 우회용 `X-Member-Id` 기반 필터는 운영에서 사용하지 않는다.

## 10. 외부 서비스 가입 및 설정

### 10.1 Toss Payments

1. Toss Payments 개발자 콘솔에서 테스트 또는 운영 키를 발급한다.
2. Backend에는 `TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`를 설정한다.
3. Frontend 빌드에는 `VITE_TOSS_CLIENT_KEY`를 설정한다.
4. 운영 Kubernetes에서는 `toss-secret`에 `client-key`, `secret-key`로 저장한다.

### 10.2 Firebase Cloud Messaging

1. Firebase Console에서 프로젝트를 생성한다.
2. Android 앱 또는 Web 앱을 등록한다.
3. Android 시연앱에는 `android/app/google-services.json`을 배치한다.
4. PWA에는 `VITE_FIREBASE_*` 환경변수를 설정한다.
5. 서버 발송 시연이 필요하면 Firebase 서비스 계정 JSON을 준비하고, seed 또는 운영 secret 주입 절차에 맞게 등록한다.

### 10.3 Gmail SMTP

1. Gmail 계정에서 앱 비밀번호를 발급한다.
2. Kubernetes `mail-secret`에 `username`, `password`로 저장한다.
3. API deployment의 `MAIL_HOST=smtp.gmail.com`, `MAIL_PORT=587` 설정을 확인한다.

### 10.4 OpenAI

1. OpenAI API key를 발급한다.
2. Kubernetes `openai-secret`의 `api-key`로 저장한다.
3. `SPRING_AI_MODEL_CHAT=openai`를 설정하면 AI 기능이 활성화된다.
4. `OPENAI_MODEL`은 현재 배포 매니페스트 기준 `gpt-5.4-mini`를 사용한다.

   - 대시보드 또는 이벤트 화면에서 수집 결과 확인
4. 세그먼트 생성
   - 이벤트 조건, 유저 태그 조건을 조합해 세그먼트 생성
   - Worker의 세그먼트 빌드 완료 후 대상자 수 확인

### 12.3 장애 시 대체 시나리오

- FCM 실기기 푸시가 실패하면 `backend/scripts/demo-inject`의 이벤트 주입 스크립트로 이벤트 발생을 대체한다.
- ClickHouse 장애 시 `BUTTERFLY_CLICKHOUSE_ENABLED=false`로 변경해 MySQL 기반 세그먼트 빌드로 롤백한다.
- SMTP 장애 시 메일 발송 대신 알림 로그와 캠페인 실행 상태 중심으로 시연한다.
- Frontend 배포 장애 시 로컬 `npm run dev` 서버로 접속해 API만 운영 서버를 바라보게 한다.

## 13. 배포 특이사항

- API와 Worker의 ClickHouse 토글 값은 반드시 동일하게 유지한다.
- Flyway migration은 API만 수행한다. Worker는 `SPRING_FLYWAY_ENABLED=false`를 유지한다.
- Worker는 web application type이 `none`이므로 Kubernetes HTTP probe를 사용하지 않는다.
- Jib 이미지의 JVM heap 비율은 `backend/build.gradle`의 `-XX:MaxRAMPercentage=60.0`을 기준으로 한다.
- 운영 인증은 `prod` 프로파일에서 JWT 기반으로 동작한다.
- 실제 secret 파일, Firebase service account, DB dump의 개인정보 포함 여부는 제출 전 반드시 검토한다.

## 14. 제출 파일 체크리스트

`exec` 폴더에 다음 파일을 포함한다.

```text
exec/
  포팅_매뉴얼.md
  butterfly_dump_latest.sql
```

선택적으로 시연 보조 문서를 함께 넣을 수 있다.

```text
exec/
  demo_scenario.md
  external_services.md
```

제출 전 확인:

- 폴더명이 정확히 `exec`인지 확인
- 소스코드 전체를 `exec`에 중복 업로드하지 않았는지 확인
- DB 덤프에 불필요한 개인정보나 운영 secret이 포함되지 않았는지 확인
- Firebase service account JSON, SSH key, API token 등 민감 파일이 포함되지 않았는지 확인
- 매뉴얼의 URL, 계정, 포트, 이미지 namespace가 실제 제출 환경과 일치하는지 확인
