# 한국형 멀티테넌트 CRM 캠페인 SaaS 요구사항 정리

문서 목적: 아키텍처 설계 문서를 바탕으로, 본 프로젝트의 기능/비기능 요구사항과 개발 범위, 제약 조건, 완료 기준을 정리한다.
팀 구성 기준: 6인 팀 (안 C. 도메인 기준 백엔드 우선 분리 후 프론트 공동 구현 버전)

---

## 1. 프로젝트 개요

### 1-1. 프로젝트 명

한국형 멀티테넌트 CRM 캠페인 SaaS (가칭)

### 1-2. 한 줄 정의

`고객 행동 데이터 수집 -> 세그먼트 계산 -> 캠페인/플로우 실행 -> 성과 분석`의 흐름을 하나의 플랫폼으로 묶은 CRM 운영 엔진.

### 1-3. 제품 포지셔닝

- 단순 메시지 발송 툴이 아님
- 고객 행동 데이터를 수집하고, 판단하고, 실행하고, 측정하는 흐름을 하나의 제품으로 연결
- MVP 채널은 `앱 푸시`, `웹 푸시` 우선 지원
- 이후 카카오, SMS, 이메일로 확장 가능한 구조

### 1-4. 목표 사용자

- 브랜드, 서비스, 앱 운영자
- 마케터, CRM 담당자, 분석가, 개발자
- 대행사형 운영자 (향후 확장)

---

## 2. 프로젝트 목표

### 2-1. 비즈니스 목표

1. 국내 환경에 맞는 멀티테넌트 CRM 운영 플랫폼을 만든다.
2. 단순 발송이 아니라 `성과 측정`까지 고려한 구조를 구현한다.
3. 카카오, SMS, 이메일로의 확장을 대비한 채널 추상화 구조를 확보한다.

### 2-2. 기술 목표

1. 멀티테넌트 구조를 기본 전제로 설계한다.
2. 이벤트 수집 -> 세그먼트 평가 -> 캠페인/플로우 실행 -> 성과 분석의 흐름이 끊기지 않게 구현한다.
3. 비동기 처리와 확장 가능한 채널 구조를 가진다.
4. MVP에서는 구현 가능성과 운영 안정성을 우선한다.
5. 향후 기능 확장 시 구조를 크게 뒤엎지 않는다.

### 2-3. 팀 운영 목표

1. 6인 팀이 SSAFY 프로젝트 기간 안에 완성 가능한 범위로 설계한다.
2. 역할 경계를 백엔드 도메인 기준으로 명확히 나눈다.
3. 후반부에 프론트엔드 작업이 몰리지 않도록 공통 규칙을 선제적으로 정한다.

## 3. 기능 요구사항

### 3-1. 인증 / 테넌트 / 프로젝트 / 권한

#### 필수 기능

1. 이메일/비밀번호 기반 로그인 및 로그아웃
2. JWT 기반 세션 관리
3. Tenant 생성 및 관리
4. Project 생성, 전환, 기본 정보 관리
5. 프로젝트 멤버 초대 및 권한 관리
6. 역할 기반 접근 제어 (관리자, 운영자, 분석가, 개발자)
7. 모든 API는 `project_id` 기준 접근 권한 검증

#### 선택 기능

1. 소셜 로그인 (MVP 이후 검토)
2. 대행사형 운영을 위한 다중 Tenant 관리 UI

#### 완료 기준

- 사용자가 로그인 후 자신의 권한이 있는 프로젝트만 조회 및 전환할 수 있다.
- 권한이 없는 API 호출은 모두 거부된다.
- 프로젝트 멤버 권한 변경은 감사 로그에 기록된다.

---

### 3-2. 고객 / 이벤트 수집 / 프로필

#### 필수 기능

1. SDK 또는 서버 API를 통한 이벤트 수집
2. 이벤트 기본 검증 및 프로젝트 기준 스키마 검사
3. 이벤트 큐 적재 (비동기 처리)
4. 고객 식별자 관리 및 통합
5. 고객 속성 관리
6. 디바이스 정보 관리
7. 고객 상세 프로필 조회
8. 이벤트 조회 API

#### 선택 기능

1. 이벤트 스키마 관리 UI
2. 고객 머지 (동일 고객의 여러 디바이스 통합) 규칙 관리

#### 완료 기준

- 이벤트 수집 API는 빠르게 응답하고, 실제 저장은 워커에서 처리한다.
- 동일 고객의 여러 디바이스가 하나의 고객 히스토리로 조회된다.
- 잘못된 이벤트는 검증 실패 로그 또는 DLQ에 기록된다.

---

### 3-3. 세그먼트 엔진

#### 필수 기능

1. 세그먼트 정의 저장 (조건 트리 구조)
2. 세그먼트 빌더 UI 및 API
3. 조건 해석 및 대상 고객 계산
4. 세그먼트 미리보기 제공 (예상 모수)
5. AND/OR 중첩 조건 지원
6. 이벤트 조건, 속성 조건, 기간 조건 지원

#### 선택 기능

1. SegmentSnapshot 테이블 기반 스냅샷 기능
2. 고객별 세그먼트 포함 상태 테이블
3. 고빈도 세그먼트 전용 물질화 뷰

#### 완료 기준

- 운영자가 UI 상에서 세그먼트 조건을 구성하고 예상 모수를 즉시 확인할 수 있다.
- 이벤트 발생 시 관련 세그먼트만 부분 갱신된다.
- 세그먼트 미리보기 응답 시간은 일반적인 조건에서 수 초 내외다.

---

### 3-4. 캠페인 / 템플릿 / 채널 설정

#### 필수 기능

1. 단발 및 예약 캠페인 생성
2. 대상 세그먼트 연결
3. 메시지 템플릿 저장 및 변수 치환
4. 발송 직전 메시지 확정 (`CampaignMessage`)
5. 프로젝트별 채널 자격 증명 관리 (암호화 저장)
6. 채널별 기본 설정 화면
7. 발송 작업 생성

#### 선택 기능

1. A/B 테스트 메시지 버전 관리
2. 템플릿 미리보기 렌더링

#### 완료 기준

- 템플릿이 나중에 변경되어도 과거 발송 이력을 안정적으로 재현할 수 있다.
- 채널 자격 증명은 평문으로 저장되지 않고, 마스킹되어 표시된다.
- 자격 증명 수정 및 조회는 감사 로그에 기록된다.

---

### 3-5. 자동화 플로우 / 발송 엔진

#### 필수 기능

1. 플로우 정의 저장 (노드/분기 구조)
2. 트리거 이벤트 기반 실행 시작
3. 단계별 다음 액션 계산 (대기, 분기, 조건 평가, 메시지 발송)
4. 플로우 실행 상태 관리
5. 채널별 발송 작업 생성
6. 속도 제한 적용
7. 재시도 정책 수행 (일시적 실패 vs 영구 실패)
8. 채널 어댑터를 통한 외부 채널 호출
9. 발송 결과 로그 저장

#### 선택 기능

1. 플로우 편집 중 실행 상태 분리 관리 (버전 충돌 방지)
2. 발송 상태 실시간 모니터링 화면

#### 완료 기준

- 플로우 정의와 실행 이력이 분리되어 저장된다.
- 일시적 실패는 제한된 횟수만 재시도되고, 영구 실패는 즉시 실패 로그에 기록된다.
- 반복 실패 데이터는 DLQ로 이동한다.
- 채널 어댑터 구조를 통해 새로운 채널을 추가할 때 상위 로직을 크게 수정하지 않는다.

---

### 3-6. 분석 / 대시보드 / 리포트

#### 필수 기능

1. 발송 수, 성공 수, 오픈 수, 클릭 수, 전환 수 집계
2. 캠페인별 성과 리포트
3. 채널별 성과 비교
4. 세그먼트별 성과 조회
5. 집계 테이블 기반 대시보드 조회
6. 전환 이벤트 기록

#### 선택 기능

1. 코호트 분석
2. 리텐션 분석
3. 퍼널 분석
4. 매출 기여 분석

#### 완료 기준

- 운영 UI는 집계 테이블을 우선 조회하여 응답 속도를 보장한다.
- 일/시간 단위 집계가 정기적으로 갱신된다.
- 캠페인, 채널, 세그먼트 단위의 성과 비교가 가능하다.

## 4. 비기능 요구사항

### 4-1. 성능

1. 이벤트 수집 API 응답은 빠르게 반환한다 (무거운 처리는 워커에서 수행).
2. 세그먼트 미리보기는 캐시와 인덱싱을 활용해 응답 속도를 확보한다.
3. 운영 대시보드는 집계 테이블을 우선 조회한다.
4. 예약 발송 시간대의 집중 트래픽에 대응할 수 있는 워커 수평 확장 구조를 갖춘다.

### 4-2. 확장성

1. 워커 수평 확장 가능
2. 발송 큐 분리 가능
3. 채널 어댑터 독립 서비스화 가능
4. 분석 저장소 확장 가능
5. 새로운 채널 추가 시 상위 로직 변경 최소화

### 4-3. 보안

1. 채널 자격 증명은 암호화 저장 및 마스킹 표시
2. 민감 정보 수정/조회는 감사 로그에 기록
3. 모든 API는 인증 및 `project_id` 기준 인가를 거친다.
4. JWT 기반 세션 관리

### 4-4. 안정성 및 장애 대응

1. 재시도 정책 구현 (일시적 실패는 제한된 재시도, 영구 실패는 즉시 실패 기록)
2. 반복 실패는 DLQ로 이동
3. 구조화된 운영 로그 (request_id, tenant_id, project_id, campaign_id, flow_execution_id, channel_type, delivery_status)
4. 큐 적체량, 발송 성공률, 채널별 실패율, 세그먼트 계산 시간, API 에러율, 워커 처리 시간 관측

### 4-5. 멀티테넌트

1. 조직 상위 단위는 `Tenant`, 실제 데이터 분리는 `Project`
2. 모든 핵심 도메인 테이블은 `tenant_id` 또는 `project_id`를 가진다.
3. MVP는 `공유 DB + 공유 스키마 + project_id 기반 논리 분리`로 시작
4. 향후 엔터프라이즈 요구 시 물리 분리 가능한 구조 유지

### 4-6. 관측성

1. 필수 운영 지표 수집
2. 구조화 로그 저장
3. 감사 로그 대상 명확화 (권한 변경, 채널 자격 증명 수정, 캠페인 활성화/중지, 플로우 활성화/비활성화, 대량 발송 실행)

## 5. 기술 스택

### 5-1. 프론트엔드

- `React` + `Next.js` 또는 `Vite + React`
- 관리 콘솔 중심 UI
- 공통 컴포넌트 라이브러리 구성

### 5-2. 백엔드

- `Spring Boot` 또는 `NestJS` 중 팀 역량에 따라 선택
- REST API 중심
- 모듈형 모놀리식 구조
- API 프로세스와 Worker 프로세스 분리

### 5-3. 데이터베이스 및 인프라

- `PostgreSQL` (주 저장소)
- `Redis` (캐시, 분산 락, 큐 브로커 보조)
- `RabbitMQ` 또는 `Redis 기반 큐`
- 오브젝트 스토리지 (템플릿 자산 저장 용도, 필요 시)

### 5-4. 선택 기준

- 팀이 Java/Spring에 강하면 `Spring Boot + PostgreSQL + Redis`
- 팀이 TypeScript/Node에 익숙하면 `NestJS + PostgreSQL + Redis`
- 언어보다 중요한 것은 도메인 분리, 비동기 처리, 멀티테넌트 규칙의 일관된 구현

## 6. 개발 범위 (Scope)

### 6-1. MVP 포함 범위

- 인증/테넌트/프로젝트/권한
- 고객/이벤트 수집/프로필
- 세그먼트 엔진 (저장, 미리보기, 평가)
- 캠페인/템플릿/채널 설정
- 자동화 플로우/발송 엔진 (앱 푸시, 웹 푸시)
- 기본 분석 대시보드

### 6-2. MVP 제외 범위

- 카카오 비즈메시지, SMS, 이메일 채널
- 코호트/리텐션/퍼널/매출 기여 고도화 분석
- AI 기반 추천 기능 (세그먼트, 발송 시점, 채널, 메시지 카피)
- 대형 고객사 전용 물리 분리 DB
- 소셜 로그인

### 6-3. 향후 확장 범위

1. 채널 확장: 카카오, SMS, 이메일 어댑터 추가
2. 분석 확장: 코호트/리텐션/퍼널/매출 기여 분석
3. AI 확장: 세그먼트 추천, 발송 시점 추천, 채널 추천, 메시지 카피 초안 추천

---

## 7. 제약 조건

### 7-1. 일정 제약

- SSAFY 프로젝트 기간 내 MVP 완성 필요
- 후반부 프론트엔드 작업 집중에 따른 UI 일정 리스크 존재

### 7-2. 인력 제약

- 총 6명
- 백엔드 우선 분리, 프론트엔드 공동 구현 방식 (안 C)

### 7-3. 기술 제약

- 초기에는 모놀리식 구조 + 별도 워커로 구현
- 마이크로서비스 구조는 도입하지 않는다.
- 분산 시스템 복잡도는 최소화한다.

### 7-4. 운영 제약

- 장애는 숨기지 않고 재시도, 실패 로그, 감사 로그, DLQ로 추적 가능해야 한다.
- 민감 정보는 평문 저장 금지

---

## 8. 팀 역할 분리 (안 C 기반)

### 8-1. 기본 원칙

1. 1차로 6명이 백엔드 도메인 역할을 나눠 서버 기능을 먼저 구현한다.
2. 2차로 전원이 프론트 화면 구현에 같이 붙는다.
3. 각자 백엔드에서 맡았던 도메인 화면의 주도자가 된다.

### 8-2. 백엔드 역할 분리

| 역할 | 담당 영역 | 핵심 산출물 |
|------|----------|------------|
| 1 | 인증 / 테넌트 / 프로젝트 / 권한 | 로그인 API, 권한 API, 프로젝트 관리 API |
| 2 | 고객 / 이벤트 수집 / 프로필 | 이벤트 수집 API, 고객 조회 API, 프로필 구조 |
| 3 | 세그먼트 엔진 | 세그먼트 저장 API, 미리보기 API, 계산 로직 |
| 4 | 캠페인 / 템플릿 / 채널 설정 | 캠페인 API, 템플릿 API, 채널 설정 API |
| 5 | 자동화 플로우 / 발송 엔진 | 플로우 API, 발송 워커, Delivery 로그 |
| 6 | 분석 / 대시보드 / 통합 검증 | 분석 API, 집계 로직, 통합 점검 |

### 8-3. 프론트엔드 공동 구현 단계 주도자

1. 역할 1: 로그인, 프로젝트 선택, 권한 화면
2. 역할 2: 고객, 이벤트 화면
3. 역할 3: 세그먼트 화면
4. 역할 4: 캠페인, 템플릿, 채널 화면
5. 역할 5: 플로우, 발송 상태 화면
6. 역할 6: 대시보드, 리포트 화면 및 전체 통합

### 8-4. 이 안의 리스크와 대응

- 리스크: 후반부 프론트 작업 집중
- 대응: 공통 규칙을 1주차에 선제적으로 확정

## 9. 공통 규칙 (1주차 선행 합의 필수)

### 9-1. API 및 백엔드 공통 규칙

1. 공통 API 응답 포맷
2. 공통 에러 처리 방식 및 에러 코드 체계
3. 인증 방식 및 `project_id` 전달 규칙
4. 이벤트명, 속성명, 채널 타입 등 enum 확정
5. 공통 ERD 확정

### 9-2. 프론트엔드 공통 규칙

1. 공통 라우팅 구조
2. 공통 레이아웃 (사이드바, 헤더)
3. 공통 컴포넌트 규칙 (테이블, 폼, 버튼)
4. 권한에 따른 메뉴 노출 처리 규칙
5. 화면 우선순위 및 디자인 가이드

### 9-3. 운영 공통 규칙

1. 구조화 로그 필드 표준 (request_id, tenant_id, project_id 등)
2. 감사 로그 대상 범위
3. 배포 환경 및 환경 변수 관리 규칙
4. 커밋 메시지, 브랜치 전략, 코드 리뷰 규칙

---

## 10. 개발 일정 제안

### 10-1. 1주차 - 선행 합의 및 기반 구조

1. 공통 ERD 확정
2. API 응답 포맷 규칙 확정
3. 인증 방식과 `project_id` 전달 규칙 확정
4. 이벤트명/속성명/채널 타입 enum 확정
5. 프론트 공통 레이아웃과 라우팅 확정
6. 배포 환경 기초 구성

### 10-2. 백엔드 병렬 개발 시작 순서

1. 역할 1: 인증/권한 뼈대 우선 완성
2. 역할 2: 고객/이벤트 적재 구조 완성
3. 역할 3: 세그먼트 저장 구조와 미리보기 API 구현
4. 역할 4: 캠페인/템플릿/채널 설정 화면과 API 구현
5. 역할 5: 플로우/발송 워커 구조 구현
6. 역할 6: 대시보드와 분석 집계 구조 구현

### 10-3. 중간 통합 순서

1. 이벤트 수집 -> 고객 프로필 조회 연결
2. 고객/이벤트 -> 세그먼트 계산 연결
3. 세그먼트 -> 캠페인 생성 연결
4. 캠페인/플로우 -> 발송 로그 연결
5. 발송 로그 -> 분석 대시보드 연결

### 10-4. 프론트 공동 구현 단계

- 백엔드 기능이 어느 정도 정리된 시점부터 전원이 프론트에 붙는다.
- 각자 백엔드에서 맡은 도메인 화면의 주도자가 된다.

## 13. 완료 기준 (Definition of Done)

### 13-1. 기능 완료 기준

1. MVP 범위의 모든 필수 기능이 동작한다.
2. 이벤트 수집부터 분석까지 end-to-end 흐름이 끊기지 않고 동작한다.
3. 멀티테넌트 권한 분리가 모든 API에 일관되게 적용된다.
4. 앱 푸시, 웹 푸시 채널로 실제 발송이 성공한다.

### 13-2. 품질 기준

1. 재시도, 실패 로그, DLQ가 동작한다.
2. 감사 로그가 지정된 이벤트에 대해 기록된다.
3. 운영 대시보드가 집계 테이블 기반으로 응답한다.
4. 주요 API에 대한 통합 테스트가 존재한다.

### 13-3. 발표 기준

1. 시스템 아키텍처 다이어그램 준비 완료
2. 이벤트 수집 -> 세그먼트 -> 캠페인 -> 분석 흐름의 데모 시연 가능
3. 멀티테넌트, 비동기 처리, 채널 추상화, 성과 측정 관점의 설명 가능

---

## 14. 발표 강조 포인트

1. 멀티테넌트가 처음부터 고려된 구조라는 점
2. 이벤트/세그먼트/자동화의 실시간성을 비동기로 안정화했다는 점
3. MVP는 모놀리식이지만, 워커와 채널 어댑터로 확장 가능성을 확보했다는 점
4. 단순 발송이 아니라 성과 측정까지 고려한 구조라는 점
5. 6인 팀의 도메인 기준 역할 분리로 책임 범위가 명확하다는 점
