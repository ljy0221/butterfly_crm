# CI integration-test OOMKilled(exit 137) — 2단계 fix 사이클

## 한 줄 요약

**1차 가설 "JVM 내 컨테이너 공유로 메모리 정점 완화"는 옳았으나 충분하지 않았다. 모듈 간 fork JVM 동시성을 놓쳐 OOM이 재발했고, workers.max 4→2로 동시 모듈 수를 절반으로 줄여 닫았다. 1차 fix가 "효과 없음"이 아니라 "필요하지만 충분하지 않음"이었다는 인식이 본 카드의 핵심 학습 포인트.**

## Context (배경)

### 직전 작업

- **MR #96** ([ci-gate-restoration](../optimizations/2026-05-07_ci-gate-restoration.md)) 머지로 5/15 DoD "CI 그린"이 측정 가능해짐. `allow_failure: true` 제거로 RED가 RED로 보고됨.
- **MR #99** (frontend CI 도입) 1차 push — 본 사이클의 트리거. frontend 작업이지만 `.gitlab-ci.yml` 변경으로 backend 잡까지 트리거됨 (안전망 동작, 별도 학습 포인트).

## Timeline (사고 흐름 그대로)

### 단계 1: 발견 — 첫 OOM RED

- **계기**: 사용자가 frontend CI MR(#99) 1차 push 결과를 공유. 잡 로그 끝에:

  ```text
  ERROR: Job failed (system failure):
  Error in container build: exit code: 137, reason: 'OOMKilled'
  ```

- **발견 시점 컨텍스트**: backend integration-test 잡 진행 중. frontend 작업 push인데 backend 잡이 도는 이유는 `.gitlab-ci.yml` 변경 시 모든 잡 트리거되는 안전망 때문 (본 카드 범위 외 별도 학습 포인트).

- **Before 측정 (직전 GREEN)**: MR #96 2차 push run (commit `56b0e5e`)에서 integration-test 단일 잡 8m 24s GREEN 으로 측정됨. 같은 코드베이스 + `.gitlab-ci.yml`이 단 하루 만에 OOM으로 전환된 것은 **모듈 간 동시 진입 타이밍**이 외부 변수(캐시 적중률 등)로 흔들렸음을 시사.

### 단계 2: 첫 가설 — K8s 메모리 한도 초과 + 동시성 정점

- **추정 (정직성: 모두 추정값)**:
  - butterfly-worker / butterfly-reporting / butterfly-api 3개 통합 테스트가 거의 동시에 진입한 직후 죽음
  - 각 통합 테스트가 TestContainers + Spring Context + Kafka 등을 각자 띄움
  - JVM heap 3개 + TestContainers MySQL 컨테이너들이 한꺼번에 메모리 점유

- **직전 GREEN과의 차이 추정**:
  - MR #96 2차 측정(8m 24s 그린) 대비 차이는 캐시가 더 적게 적중해 모듈들이 시간상 분산되어 동시 메모리 정점이 낮았기 때문일 가능성
  - **즉, 직전 GREEN은 "운 좋게 정점이 어긋났을 뿐"이라는 가설**

- **추정과 실측 분리**:

  | 항목 | 종류 | 값 |
  |---|---|---|
  | exit code | 실측 | `137` (SIGKILL by OOM killer) |
  | 메모리 정점 | 추정 | 4 × 256MB heap + N × MySQL container (정확값 불명) |
  | K8s pod memory limit | 미측정 | Runner config 접근 권한 없음 |
  | 어느 프로세스가 정점 찍었는지 | 측정 불가 | OOM 로그가 알려주지 않음 |

### 단계 5: 진단 재구성 — 1차 가설의 한계 인식 (★ 핵심 학습 포인트 ★)

> **"1차 fix가 효과 없음이 아니라, 필요하지만 충분하지 않음이었다"** 는 인식 전환.

#### 컨테이너 공유의 효과 범위 — 좁혀진 이해

| 효과 범위 | 1차 fix 적용 |
|---|---|
| **같은 모듈 내 클래스 간** (= 같은 fork JVM) | ✅ 적용 — MySQL 컨테이너 1개 공유 |
| **모듈 간** (= 서로 다른 fork JVM) | ❌ 적용 안 됨 — 각 모듈이 별도 fork JVM이라 컨테이너 인스턴스 공유 불가 |

#### 동시 메모리 정점 재구성

4개 통합 테스트 잡(api/event/campaign/reporting)이 여전히 동시 진행 시:

```text
모듈 4개 × Spring 전체 컨텍스트 로드
모듈 4개 × MySQL TestContainer (모듈마다 별도 fork JVM이라 공유 안 됨)
모듈 4개 × JVM heap
```

→ **모듈 간 동시성이 메모리 정점의 진짜 원인**이라는 가설로 전환.

### 단계 6: 2차 fix — Gradle workers.max 4→2 (commit `ab7372e`)

#### 변경

- `.gitlab-ci.yml`의 `GRADLE_OPTS`에서 `workers.max` 4 → 2

#### 효과 추정

| 항목 | Before (1차 fix만) | After 2차 fix |
|---|---|---|
| 동시 실행 모듈 수 | 4 | 2 |
| 모듈당 컨테이너 점유 | (1차 fix로 모듈 내 공유) | 동일 |
| **메모리 정점 (추정)** | 4 모듈 × heap + 4 컨테이너 인스턴스 | **약 절반** |

#### 1차 fix와의 관계

- **둘 다 필요**:
  - 1차 fix: 같은 모듈 내 컨테이너 중복 제거
  - 2차 fix: 모듈 간 동시성 절반
- **하나만으로는 부족**:
  - 1차 fix만 → 모듈 간 정점은 그대로
  - 2차 fix만 → 같은 모듈 내 중복은 그대로

#### push 결과 — 통합 테스트 그린, OOM 차단 확인

| 항목 | Before (1차 fix push, OOMKilled) | After (2차 fix push, GREEN) |
|---|---|---|
| 종료 코드 | exit 137 (OOMKilled) | 정상 종료 |
| integration-test 잡 결과 | 시스템 강제 종료 (테스트 미완) | 그린 |
| 전체 pipeline wall-clock | (잡 죽어서 측정 불가) | **10m 56s 실측** |

**정직성 메모 — 실측 wall-clock 해석의 한계**:
- 10m 56s가 OOM 직전 정상 측정(MR #96 2차의 10m 53s)과 거의 동일.
- 이번 push는 backend/* 변경(테스트 코드 import + ddl-auto 옵션)만 있고
  production 코드/build.gradle/gradle.properties는 무변경 →
  **Gradle Build Cache 적중이 매우 높을 것으로 추정** (직전 캐시와 같은 키).
- 즉 wall-clock은 "workers.max=2가 시간을 늘렸는가"에 답하지 못함.
- 진짜 측정은 다음 production 코드 변경 push에서 콜드 캐시 wall-clock을 봐야 함.
- **현재 확정된 것**: OOM은 차단됨 (그린이 그것을 입증). 시간 비용은 캐시 효과로 묻혀 정확한 측정 보류.

## Dead Ends (막다른 길)

### Dead End 1: 광범위 EmbeddedKafka 일괄 교체 (단계 3에서 사용자 제안 후 보류)

- **시도/검토**: 모든 모듈의 Kafka TestContainer를 `@EmbeddedKafka`로 일괄 교체
- **폐기 이유**:
  1. butterfly-event는 이미 EmbeddedKafka 사용 중 — "교체"가 아니라 "확산"이며, 이미 일부 끝난 상태
  2. 5/15 D-8 시점에 도메인 테스트 코드 광범위 개편은 회귀 위험 큼
  3. OOM fix와 결합하면 변수 분리 어려움 (어느 변경이 효과 냈는지 불명)
- **재방문 트리거**: Code Freeze 5/15 후 + 2~3일 여유 + 깜빡임 재발 시
- **재방문 시 검토 항목**: 어느 모듈에 EmbeddedKafka 가능 / KRaft 모드 호환성 / Spring Boot 3.x 통합 패턴

### Dead End 2: RabbitMQ 의존성 일괄 삭제 (이번 PR에 묶기)

- **시도/검토**: 사용자가 "RabbitMQ는 더 이상 안 쓰는데 testsupport에 남아있다" 지적, 같은 PR에 삭제 검토
- **폐기 이유**:
  1. OOM fix 변수 분리: 의존성 삭제 + OOM fix가 같은 PR이면 어느 변경이 효과 냈는지 불명
  2. PR 리뷰 부담 분산
- **재방문 트리거**: OOM 사이클 종료 + 별도 PR 분리 후
- **재방문 시 검토 항목**: testsupport `AbstractRabbitMqContainerTest` 사용처 grep / 의존성 트리에서 amqp-client 잔존 여부

### Dead End 3: K8s pod memory limit 인상 (1차 시점에 검토 후 보류)

- **시도/검토**: workers.max 변경 대신 K8s pod memory limit 인상으로 한도 자체를 높이는 안
- **폐기 이유**:
  1. Runner config 접근 권한 없음 (infra 협의 필요)
  2. 5/15 D-8 시점에 외부 협의 + 변경 risk
  3. 본질적으로 메모리 사용량 자체를 줄이는 방향이 더 깔끔 (근본 원인 해결)
- **재방문 트리거**: workers.max=2 + 컨테이너 공유로도 OOM 재발 시
- **재방문 시 양자 택일**:
  - workers.max=1 (직렬화) — 잡 wall-clock 증가, 하지만 외부 협의 불필요
  - K8s pod memory limit 인상 — 잡 wall-clock 유지, infra 협의 필요

## Lessons (학습 포인트 박제)

### 다음에 비슷한 상황에서 먼저 확인할 4가지

1. **OOM 재발 시: 진짜 메모리 정점 차원 식별**
   - 같은 JVM 내 vs 모듈 간 fork JVM 구분
   - "컨테이너 공유"는 같은 JVM 내에만 효과
   - 모듈 간 정점은 `--max-workers` (Gradle) 또는 K8s pod memory limit 차원

2. **GitLab Runner OOM 로그 한계 인식**
   - exit 137 + OOMKilled 표시만 있고 어느 프로세스가 정점 찍었는지 알려주지 않음
   - 추정 → 다단계 fix → 효과 측정의 점진적 좁히기 필요
   - 가능하면 `kubectl top pod` (권한 있으면) 또는 `jstat` 로 메모리 추이 캡처

3. **사용자 광범위 제안의 신중한 평가**
   - "이미 끝난 일"을 짚어 스코프 좁히기 (예: butterfly-event는 이미 EmbeddedKafka)
   - Code Freeze 임박 시 도메인 테스트 광범위 개편 회피
   - 변수 분리 우선 (한 PR = 한 변경 의도)

4. **로컬 검증의 한계 — K8s pod memory limit 컨텍스트 부재**
   - 로컬은 컨테이너 공유 검증까지는 잡음
   - 모듈 간 동시 fork JVM의 메모리 정점은 K8s pod memory limit 컨텍스트가 없어 재현 불가
   - 다음 비슷한 작업: 가능하면 단일 잡으로 모든 모듈 직렬 실행 + JVM 메모리 모니터링 실험

### 패턴 인식 (직관 출처 박제)

- **"같은 코드베이스가 단 하루 만에 OOM"** → 외부 변수(캐시 적중률, 동시성 타이밍) 변동 가능성. 직전 GREEN이 "운 좋게 정점이 어긋남"이었을 가능성을 1순위로 의심
- **"여러 모듈이 거의 동시에 죽음"** → 모듈 간 동시성 정점이 진짜 원인. 모듈 내 최적화는 보조
- **"진짜 원인은 측정 불가, 우회로 좁혀가야 한다"** → 다단계 fix를 부끄러워하지 말 것. "1차 fix가 효과 없었다"가 아니라 "필요하지만 충분하지 않았다"

### 추정 vs 실측 분리 표 (학습용)

| 항목 | 추정 | 실측 |
|---|---|---|
| 1차 OOM 메모리 정점 | 4 × 256MB heap + N × MySQL | 측정 불가 (OOM 로그 한계) |
| 1차 fix 효과 | "모듈 내 컨테이너 공유로 메모리 정점 완화" | OOM 재발 → **부분적 효과만**, 충분하지 않음 입증 |
| 2차 fix 효과 | "동시 모듈 수 절반 → 메모리 정점 약 절반" | 결과 측정 대기 중 (2026-05-08 시점) |
| K8s pod memory limit | 미측정 (권한 없음) | — |
| exit code | — | `137` (SIGKILL by OOM killer) |

## Hindsight (사후 회고)

> 그 시점에 알았던 것 vs 지금 보면 명백한 것의 분리.

### 그 시점엔 몰랐던 것

- 1차 fix가 모듈 간 fork JVM에는 효과 없다는 사실 (이론적으로는 알았으나 동시성 정점이 결정적이라는 인식 부족)
- 직전 GREEN이 "운 좋게 정점이 어긋났을 뿐"일 가능성을 1순위로 가져갔어야 함

### 지금 보면 명백한 것

- 4개 통합 테스트 잡이 거의 동시 진입한 직후 죽음 → 모듈 간 동시성 1순위 의심이 자연스러움
- 1차 fix push 전에 workers.max 도 함께 줄였더라면 1회 push로 끝났을 가능성
- 단, **변수 분리 원칙** 관점에서는 1차+2차를 분리한 것이 효과 측정에 도움됨 (정직성)

### "더 나은 길이 있었음을 사후에 알았다"

- 단계 4의 부수효과(`expected 32 vs 34`) 발견 시 직전 CI 로그의 `drop table if exists devices` 단서를 더 빨리 연결했더라면 검증 1라운드 단축 가능
- 단, 그 시점엔 컨테이너 공유 부작용 가능성을 깊이 의심하지 않음 — 다음에 컨테이너 공유 작업 시 **"이전 테스트의 schema 잔재가 남는다"** 항목을 체크리스트에 추가
